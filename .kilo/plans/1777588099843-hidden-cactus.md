# Plan: gh-commit - AI-Powered Git Commit Automation

## Overview
Implement a GitHub CLI extension that automates the git commit workflow using Kilo AI Gateway to generate commit messages.

## Current State
- Repository: `github.com/involvex/gh-commit`
- Language: Go 1.26+
- Framework: `github.com/cli/go-gh/v2` for GitHub CLI integration
- Existing code: Basic "hello world" example showing gh API usage
- Build: Uses `cli/gh-extension-precompile@v2` action

## Target Workflow
```
gh commit  (user will alias as 'ghc')
├─ git add .
├─ Get staged diff via 'git diff --cached'
├─ Call Kilo AI Gateway to generate commit message
├─ git commit -m "<generated-message>"
├─ Prompt: "Do you want to push? y/n"
└─ If yes:
   ├─ Prompt: "Do you want to push tags too? y/n"
   └─ git push [--tags if yes]
```

## Technical Requirements

### 1. API Integration
- **Endpoint**: `POST https://api.kilo.ai/api/gateway/chat/completions`
- **Auth**: `Authorization: Bearer $KILO_API_KEY` (read from environment)
- **Model**: Use `kilo-auto/small` (optimized for lightweight tasks like commit messages)
- **Request format**: OpenAI-compatible chat completion
- **System prompt**: Generate conventional commit message based on git diff

### 2. Git Operations
- Execute git commands using `os/exec` package
- `git add .` - stage all changes
- `git diff --cached` - get staged changes for AI context
- `git commit -m "..."` - create commit
- `git push` - push to remote (conditionally)
- `git push --tags` - push tags (conditionally)

### 3. User Interaction
- Interactive prompts for push confirmation
- Handle y/n input cleanly
- Display informative messages throughout

### 4. Error Handling
- Missing KILO_API_KEY environment variable
- API request failures (network, auth, rate limits)
- Git command failures
- Empty or invalid AI response

## Implementation Steps

### Step 1: Add HTTP client
- Use Go's standard `net/http` (no external deps needed)
- Implement POST request to Kilo Gateway
- Handle JSON request/response

### Step 2: Get staged changes
- Run `git diff --cached` and capture output
- Error if no staged changes (nothing to commit)

### Step 3: Generate commit message
- Build chat completion request:
  ```json
  {
    "model": "kilo-auto/small",
    "messages": [
      {"role": "system", "content": "Generate a concise conventional commit message..."},
      {"role": "user", "content": "<git diff>"}
    ],
    "max_tokens": 100,
    "temperature": 0.7
  }
  ```
- Parse response: `response.choices[0].message.content`
- Clean up the message (remove quotes, newlines, backticks)

### Step 4: Execute commit
- Run `git commit -m "cleaned-message"`
- Display the generated message to user before committing

### Step 5: Push workflow
- Prompt: "Push to remote? (y/n)"
- If yes: prompt "Push tags too? (y/n)"
- Execute appropriate git push commands

### Step 6: Testing & Validation
- Manual test with sample changes
- Verify API call structure
- Ensure proper cleanup on errors

### Step 7: Documentation
- Update README with setup instructions
- Document KILO_API_KEY requirement
- Show usage examples

## Open Questions

1. **Model selection**: Should `kilo-auto/small` be hardcoded or configurable via env var (e.g., `KILO_MODEL`)?
   - Recommendation: Hardcode `kilo-auto/small` initially, can add env override later

2. **System prompt**: Should it be customizable?
   - Recommendation: Hardcode a good conventional commit prompt initially

3. **Empty diff handling**: What if `git diff --cached` returns empty?
   - Recommendation: Abort with message "No staged changes to commit"

4. **API failure fallback**: Should we prompt user to enter message manually?
   - Recommendation: Yes, on API error, ask user to type commit message manually

5. **Commit message editing**: Should user be able to edit generated message before commit?
   - Recommendation: Show generated message and ask "Accept? (y/n/edit)" or just commit directly
   - Simplified: Commit directly, user can amend if needed

6. **Alias**: The user mentioned setting alias `ghc`. The extension will be `gh-commit`, invoked as `gh commit`. User creates shell alias `ghc='gh commit'`.

## Decision Log
- Use stdlib `net/http` (no additional dependencies)
- Non-streaming API call (simpler)
- Non-interactive commit (no editing before commit)
- Abort on API failure by default, with manual fallback option
- Conventional Commits format by default
- Windows-compatible (PowerShell) with proper shell handling
